Prompt Engineering

The cheapest adaptation technique — and the one people underestimate. A prompt is an interface you design: it has an anatomy, proven techniques, and (because users type into it) an attack surface you must defend.

Anatomy of a well-built prompt

Production prompts aren't a sentence — they're a structured document. Each part has a job.

The technique ladder

Three prompting techniques cover most needs — in this order.

Defensive prompting — the attack surface

Anywhere users (or retrieved documents!) feed text into your prompt, someone will try to abuse it.

Key takeaways

  • Prompts are structured documents System rules, context, examples, task, output format — each part has a job. Write them like production code, with versioning and tests.
  • Show, don't just tell A few good examples routinely beat long descriptions, especially for format and tone.
  • Escalate techniques by evidence Zero-shot → few-shot → chain-of-thought, moving up only when your evals say you need to.
  • Assume hostile input Users and retrieved documents can carry injected instructions. Separate data from instructions and give the model least privilege.
